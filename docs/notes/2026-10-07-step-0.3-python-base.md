# Step 0.3, part 3: Settings

Part 3 is complete. Step 0.3 is complete. A missing key stops start-up with a clear message.

## Files

| File | Contents |
|---|---|
| `pyproject.toml` | Runtime packages pydantic 2.13.5 and pydantic-settings 2.15.0. mypy plugin `pydantic.mypy` (`init_forbid_extra`, `init_typed`, `warn_required_dynamic_aliases`). |
| `apps/api/src/seo_advisor/core/config.py` | `Settings`, `load_settings()`, `SettingsError`. |
| `apps/api/tests/core/test_config.py` | 5 unit tests. |

## Decisions

- `Settings` reads only the environment. It does not read `.env` itself, because mise loads `.env` into the environment. One source, no surprise in tests.
- Every field is required. No defaults, so a missing value cannot hide.
- Fields now: `APP_ENV` (`local`, `test`, `ci`, `production`), `LOG_LEVEL` (`debug`, `info`, `warning`, `error`), `DATABASE_URL` (`SecretStr`, because it has the password). Later steps add their fields.
- `Settings` is frozen. Code cannot change it after start-up.
- `SettingsError` lists all problems together, with names and kinds only (`DATABASE_URL (missing)`, `LOG_LEVEL (invalid)`). Pydantic's own message repeats the input value, and that value can be a secret. So the code raises `from None`.
- No cached `get_settings()` yet. Step 0.5 decides how the app loads settings once at start-up.

2. mypy with the plugin found one unused `type: ignore`. I removed it.
3. `mise run check` passes (6 tests). `mise run audit`: no known vulnerabilities.
4. Start-up demo without `DATABASE_URL` and with `LOG_LEVEL=loud`: exit 1, message "Settings are missing or invalid: LOG_LEVEL (invalid), DATABASE_URL (missing). Set them in the environment or in .env (see .env.example)." The value `loud` is not in the message.
